# Core 3 B3.0 — Auditoría del contrato real de stock

**Fecha:** 2026-08-29  
**Rama:** `Core3`  
**Estado:** completada como auditoría de frontera/consumo; no modifica el contrato de producción.

## 1. Alcance

B3.0 documenta el contrato de stock que AlejoTaller consume y que B3 del panel no debe romper.

## 2. Contrato consumido

- `existence`: stock físico.
- `reserved`: unidades comprometidas por soft-hold.
- `available = existence - reserved` como regla de negocio, con protección para no mostrar negativos.
- `existence` solo disminuye al consumo de una venta VERIFIED; la creación/cancelación de pedidos afecta `reserved`.
- Las operaciones críticas de stock usan Appwrite como fuente de verdad; cache local no es autoridad.
- El operador consume el stock resultante de las entradas registradas por el panel.

La política Warehouse define explícitamente que `existence >= reserved` debe mantenerse y que el soft-hold es responsabilidad de las ventas, no de las entradas.

## 3. Frontera con compras Core 3

AlejoTaller no registra facturas de compra, no escribe `purchase_entry`, `purchase_entry_line`, `supplier` ni `last_unit_cost`, y no debe exponer operaciones MCP de abastecimiento.

El panel es el escritor canónico de compras y `last_unit_cost`; el operador consume `last_unit_cost` para COGS. La política Exchange confirma que `product.price` y `product.last_unit_cost` viven en USD y que este monorepo no registra compras ni escribe esos campos.

## 4. Consecuencia para B3

Una anulación de entrada ejecutada por el panel puede reducir `existence`, pero **no debe modificar `reserved`**. Antes de permitirla debe comprobarse que la reducción no produzca `existence < reserved`.

El operador no necesita una nueva operación de anulación. Si el contrato de `existence` o `last_unit_cost` cambia como consecuencia de B3, deberá ejecutarse el smoke del flujo de venta/COGS como validación de frontera.

## 5. `last_unit_cost`

El operador usa `last_unit_cost` como base de COGS. El panel es responsable de escribirlo. AlejoTaller no contiene el historial necesario para reconstruir un costo anterior de una entrada anulada.

Por tanto, B3.1 no debe asumir que puede restaurarse el costo anterior desde este monorepo ni introducir lógica duplicada de costos aquí.

## 6. Resultado B3.0

**Auditoría de frontera AT completada.** El contrato que debe preservarse por B3 queda documentado: `existence` físico, `reserved` soft-hold, `existence >= reserved`, cliente/operador sin escritura de compras y operador consumidor de `last_unit_cost` para COGS.
